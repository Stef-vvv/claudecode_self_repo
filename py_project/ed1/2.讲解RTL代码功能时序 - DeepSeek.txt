二、PE_Array_3x3 模块（pe_array33.v ）
1. 功能
将 3×3 个  PE 组成一个二维阵列，实现 行平稳数据流 ：
数据（in_data）广播到所有  PE （同一行数据大家共用）。
滤波器 从左向右水平传播（第  0 列接外部  in_filter ，其后接左邻  out_filter ）。
部分和 从上向下垂直传播（第  0 行接外部  in_partial_top ，其后接上邻  out_result ）。
启动信号  从左上角  start_global  开始，向右、向下分别根据  out_start  进行 OR 传播。
2. 参数与互连
ROWS=3, COLS=3 。
使用 generate  构建信号线数组，并实例化  9 个  PE 。
3. 数据广播
所有 PE 的  data_bus  均直连 in_data，即 5 个输入数据被同时送到每个  PE 。这样每个  PE 都
可以基于相同的数据窗口进行计算。
4. 滤波器水平传播
当 PE00 收到滤波器后，在完成计算时将  out_filter  传递给 PE01，依次向右流水传递。由于
PE 内滤波器被锁存在  IDLE 时，且 out_filter  是寄存器输出，所以滤波器每经过一级  PE 会
延迟一拍。
5. 部分和垂直传播
顶部 PE 的  in_partial  来自外部（一般为  0 ），其输出  out_result  成为下一行  PE 的
in_partial 。这模拟了同一列  PE 按行累加的效果。
6. 启动信号的传播
左上角 PE[0][0]  的 start 直接等于  start_global 。
其余 PE 的  start = left_start OR above_start ，其中：
left_start  来自左侧  PE 的  out_start （若 c>0）。
above_start  来自上方  PE 的  out_start （若 r>0）。
由于 out_start  在 PE 启动后维持  2 拍，所以启动脉冲会向右传播  2 列，向下传播  2 行。这种
二维传播使得阵列中的  PE 按照对角线顺序 依次激活，符合二维行平稳阵列的调度方式。
7. 输出
out_result  取最底行中间列  psum_out[2][1] 。
out_finished  取该 PE 的  finished  信号。
尽管阵列有  9 个  PE ，但由于数据流的计算特性，最终结果会在最后一行中间一列的  PE 上输出
（该列对应于卷积滑动窗的中间通道）。

多播网络（ NoC ）：输入激活和权重通过两级网络（全局多播  + 局部分发）送到目标  PE ，支

2. Eyeriss v1 如何实现 “ 可配置 ” ？
你猜得很准，其核心就是 NoC和控制逻辑 。具体来说， Eyeriss v1 主要依靠以下几点：
a.  可配置的多播网络
这是最关键的部分。 Eyeriss 的全局数据（从片外 DRAM/ 全局缓冲区取出）在送入 PE 阵列前，
会经过一个多播控制器。
不是单纯广播 ：数据不是无脑送给所有 PE ，而是根据层和映射方式， 选择性地、以不同的模
式进行多播。
多播模式 ：对于输入激活，可以配置为 “ 单播 ” （送一个 PE ）、 “ 水平多播 ” （送同一行多个
PE）或“对角线多播 ” （送对角相邻的 PE ）。对于权重和部分和，也有对应的多播模式。
工作原理 ：这就像一个可编程的 “ 发牌器 ” 。编译器（软件）算好这一层需要的数据流模式，
生成配置信息。硬件运行时，多播控制器就按照这个配置，把数据 “ 发 ” 到总线上，并附上标
签。目标 PE 识别标签后，才接收数据。
这就是 “软件配置 ” 改变硬件行为的本质 ：不是改变电路逻辑，而是 改变数据在固定电路上的分
发路径和目的地 。
b.  双缓冲和 SRAM
每个PE内部有两组寄存器或小容量 SRAM ，用于存储输入激活和权重。这允许 PE 在计算当前数
据时，就能预加载下一批数据，实现计算和数据搬移的 流水线化 。这种“预加载 ” 机制也是由控制
逻辑决定的。
c.  处理单元阵列的灵活性
12×14的阵列本身就是一个 可重配置的 2D Syst olic Ar r a y。虽然物理连线固定，但通过以上机
制，它可以在以下数据流间切换：
权重固定 ：权重保存在 PE 内，输入激活和部分和在阵列中流动。适用于卷积层。
输出 /部分和固定 ：部分和保存在 PE 内，权重和输入激活流动。适用于全连接层或某些卷积。
无固定复用 ：所有数据都流动。
这种切换不需要改变硬件结构，只需改变 数据从哪里来、到哪里去、是否保存 的控制信号即可。
3. Eyeriss v1 的复杂性

4. 软硬件接口与编译器 ：软件（编译器）必须深刻理解底层硬件的所有约束（ PE 阵列大小、存

讲解：PE 阵列（ 3x3 ）时序协作关系
在讲解时序图之前，我们先理清  3x3 阵列的时序协作关系。想象一下二维阵列中  PE 的排布：
信号的传播机制
1. 启动信号  (start_pe )
源头：外部 start_global  信号直接连接到阵列左上角的  PE[0,0]。
传播方向 ：向右和向下传播。
机制：每个 PE 内部有一个  out_start  信号，它在  PE 被启动后的  第  1、 2 拍为高（与
Verilog 代码对应， iter==1 时清零，因此维持两拍高电平）。这意味着一个  PE 的
out_start  可以覆盖它右边的两个和下方的两个  PE 。
2. 滤波器传播  (filter_in  / out_filter )
源头：外部 in_filter  信号连接到第  0 列的所有  PE 。
传播方向 ：从左向右水平传播。
机制：每个 PE 的  out_filter  实际上就是它内部锁存的  filt 寄存器。当  PE 收到
start 信号时，会锁存其输入端的滤波器。 后续时钟周期，如果其状态不在  IDLE，
out_filter  将始终保持锁存的值。
3. 部分和传播  (psum_in  / out_result )
源头：外部 in_partial_top  信号连接到第  0 行的所有  PE 。
传播方向 ：从上向下垂直传播。
机制：一个 PE 完成累加（进入  DONE 态）后，其  out_result  输出最终的部分和，供正
下方的 PE 在其累加阶段使用。

我们已经有  pe_array.py  的源代码。它从  pe.py 导入 PE，定义 PEArray 类。目标是模拟  3x3 的  PE
阵列，实现行平稳数据流：数据广播，滤波器水平传播，部分和垂直传播，启动信号对角传播。
分析 pe_array.py :
__init__(self, n, data_port, filter_port) :
存储 n (3)
创建 self.grid  为一个 n x n 的列表，每个元素是一个  PE(3) 实例。
self.finished = 0 , self.output = 0
初始化：对所有  i, j，设置 self.grid[j][i].in_data = data_port 。注意顺序： grid[j][i]  意
为行 j 列 i。所以每一行的所有  PE 的  in_data 都指向同一个  data_port  列表对象（共享引
用）。这符合 “ 数据广播到所有  PE” 。
如果 i == 0（即第0列），设置  self.grid[j][i].in_filter = filter_port ，其他列的  PE 的
in_filter  保留默认  [0,0,0]，后续通过传播来获得滤波器。
process(self) :
设置 self.finished = 0 。
首先迭代所有  PE ，调用  pe.process_one()  推进每个  PE 一个时钟周期。
然后再次迭代所有  PE （行  j ，列  i ）进行状态传播：
滤波器向右传播：如果  i != 0，则
self.grid[j][i].in_filter = self.grid[j][i-1].filter.copy() 。注意这里使用的是左边  PE
的 filter 属性（内部锁存的滤波器）。在硬件中， out_filter  是滤波器寄存器的输出。这里
复制左边  PE 的  filter，意味着下一拍该  PE 如果启动，就可以锁存这个传播过来的滤波器。
部分和向下传播：如果  j != 0，且上方  PE 的  finished  为1，则
self.grid[j][i].in_result = self.grid[j-1][i].result.copy() 。这模拟了上方  PE 完成后，
其结果可以被下方  PE 的累加阶段使用。注意在硬件中， in_partial  直接连线，不管上方是否
完成，但下方  PE 是在累加阶段才使用  in_partial 。而这里  Python 模型中只有当上方
finished  时才会复制，确保不会过早使用未完成的结果，逻辑上没问题。
启动信号传播：计算  above_start ：如果 j != 0 且上方 PE 的  out_start[0]  为1，则为 1 ；否
则0。left_start ：如果 i != 0 且左侧 PE 的  out_start[0]  为1，则为 1 ；否则 0 。对于非左
上角的 PE ，start[0] = 1 if (above_start or left_start) else 0 。这就是启动信号的对角传
播。
最后，检查最后一行（ j = n-1）是否有任一  PE 的  finished  为1，如果有，则设置
self.output = self.grid[n-1][i].result  和 self.finished = 1  并 break 。但注意， output 被
赋值为最后一行某个  finished 的  PE 的结果，而且只取第一个遇到的  finished 的  PE 的结果。在原
始设计中，输出应该是最后一行中间  PE 的结果。但是这里只要最后一行任一  PE finished ，就取它
的结果，可能不精确，但在完整系统中， PE_Array_3x3  的 Verilog 代码是取最底行中间列
psum_out[ROWS-1][COLS/2] 。Python 的  process 方法在取  output 时没有限定中间列，只是循环
最后一行，遇到第一个  finished 就  break ，这样可能会取到列 0 或列 1 而不是列 1 。但根据启动传播，
最后完成的是最右下角的  PE （因为对角线传播），所以最后一行最右侧的  PE 可能是最后  finished
的。然而当循环检查到最后一行时， PE[2,0] 可能会先于  PE[2,1] finished 吗？根据时序： PE[2,0]
和 PE[2,1] 的启动时间不同， PE[2,0] 在周期 2 启动（从  PE[1,0] 的  out_start ）， PE[2,1] 在周期 3 启
动（从 PE[1,1] 的  out_start ），所以  PE[2,0] 会在  PE[2,1] 之前完成。如果在周期 4 检查， PE[2,0]
可能已经  finished ，循环就会取  PE[2,0] 的结果而不是  PE[2,1] 。这可能是一个  bug ，但在
Scheduler 的使用中，期望的是阵列输出一整行的结果？让我们看  Scheduler 如何使用
pe_array.output 。在 scheduler.py  中，process_step  调用每个  pe_array 的  process() ，然后
aggregator 后续处理  pe_cluster[i].output 。在 aggregator.py  的 process 中，对于每个
pe_clust er ，如果  finished ，则取  self.pe_cluster[i].output ，并按照  i 索引加到输出行：最后一
个 PE clust er 特殊处理，其他的每个  PE clust er 贡献三个输出。这里的
self.pe_cluster[i].output  应该是该  PEArray 计算出的三个结果。所以  PEArray 的  output 应
该是长度为 3 的列表。但是  pe_array.py  的 output 被赋值为  self.grid[n-1][i].result ，这是
一个包含 3 个整数的列表，所以没问题。但可能存在取错列的问题：阵列有 3 列，每列的  PE 负责计
算不同的输出特征位置。我们希望  PEArray 的输出来自最后一行中间列（即列 1 ）的结果，因为那才
是完整卷积窗口滑动后正确的三个输出（对应数据窗口的三个位置）。如果取了列 0 ，那么只有数据
窗口的一部分计算结果，是不正确的。因此  Python 的  PEArray 的输出选择存在问题。但让我们检
查 Verilog 中的  PE_Array_3x3 ：assign out_result = psum_out[ROWS-1][COLS/2]; ，确实是取中
间列。在  Python 中，应该修正为取最后一行中间列的  PE 结果。
此外，关于  PEArray 与其他模块的配合， Scheduler 每次调用  process_step  会先让所有  pe_array
执行 process() ，然后 aggregator 执行  process() ，然后 write_ram 执行  process() 。在
aggregator 中，当  pe_cluster[0].finished  为1时，才处理所有  pe_clust er 。这需要所有  PEArray
同步完成。因为  Scheduler 控制整个流程的循环，在  run() 中，每层每行循环，会启动一轮计算，然
后多次调用  process_step  来推进时钟。所以  PEArray 的  process 方法需要多个时钟周期才能完成一
次完整的计算。 Python 模型中， process 被调用一次代表一个时钟周期，阵列逐步执行。在
Scheduler 的  run() 中，在某个循环内，会调用  self.process_step() ，而 process_step  只调用一
次每个 pe_array 的  process() 。这意味着  Scheduler 的循环每次迭代只推进一个时钟周期。这符合
硬件行为：在硬件中，每次时钟上升沿，整个阵列前进一步。所以  Python 的  Scheduler 通过多次循
环来模拟时钟。

一、PEArray 的核心使命：模拟行平稳数据流的二维传播
PEArray 把一个 3×3 的  PE 网格组织成一个 行平稳计算阵列 ，它的 process()  方法模拟了一
个时钟周期内所有  PE 的并行执行，以及信号在阵列中的传播。关键在于两个步骤：
1. PE 自身状态更新 （模拟寄存器 / 状态机走一步）
2. 信号传播 （模拟组合逻辑连线，为下一拍准备输入）
这种顺序执行的方式，精确地等效于硬件中的同步时序。PE 同时更新状态。 Python 的  process 方法中，先执行所有  PE 的  process_one （即组合逻辑和状态
更新），然后根据更新后的  PE 输出（out_start , filter, result）来设置下一个  PE 的输入（
in_filter , in_result , start），这些输入将在 下一次 process 调用时被  PE 使用。这正确模拟了
同步时序：信号传播一个时钟周期。所以  pe_array.py  的 process 逻辑基本正确，除了输出列的选
择缺陷。
我们再看  pe_array.py  中数据广播：所有  PE 的  in_data 都指向同一个列表，这是正确的，因为数据
在所有 PE 中同时可用。
滤波器传播：初始化时，只有第 0 列的  in_filter  被设置。在第一拍时，第 0 列  PE 可能启动并锁存滤
波器，同时其内部的  filter 被更新。然后在同一  process 调用的传播阶段，第 1 列  PE 的
in_filter  被设置为第 0 列  PE 的  filter.copy() 。所以在下一拍，第 1 列  PE 如果启动，就会锁存这
个滤波器。这与硬件中通过  out_filter  连线一致。
部分和传播：初始化时，所有  PE 的  in_result  默认 [0,0,0,0,0] 。在 Scheduler 中，顶部部分和输
入是0。当上方  PE 完成  (finished==1) ，才将其  result 复制给下方  PE 的  in_result 。在硬件中，
部分和是直接连线的，无论上方  PE 是否完成，连线上的值就是上方  PE 的  out_result 。如果上方  PE
未完成，其  out_result  可能是旧值或 0 ，但这不会影响下方  PE ，因为下方  PE 只在累加阶段
（ACC）使用该值，而此时上方  PE 一定已经完成（在行平稳数据流中，垂直方向是流水线式的，当下
方 PE 进入  ACC 时，上方  PE 应已进入  DONE ）。 Python 模型通过检查  finished  来确保不会使用无
效数据，这也是一种安全机制，但不完全反映硬件连线，但结果是一致的，因为时序保证了完成顺序。
所以没问题。
结论：pe_array.py  总体正确，但需要修正输出选取逻辑，应取最后一行中间列的  PE 结果。此外，
PEArray 的 process 方法调用了两次  for j in range(n) for i in range(n)  循环，这在  Python 中
代表了同个时钟周期内的两个阶段： PE 更新和信号传播。这正确模拟了同一周期内组合逻辑传播和寄
存器更新。但是需要注意， process_one  内部可能依赖于  start 等信号，而这些信号在传播阶段才更
新，所以同一周期内， PE 内部更新和启动信号的传播发生在同一个  process 调用内，但是有时间顺
序：先 PE 更新，再传播启动信号给其他  PE 。这相当于：在时钟沿，所有  PE 采样其输入（包括
start）并进行状态转换，然后输出新的  out_start 。这个新的  out_start 在下一个时钟沿才会被其他  PE
采样。但  Python 代码中，先计算了所有  PE 的状态更新，此时  start 还是之前的值。然后传播阶段，
我们用刚刚计算出的  out_start 来更新邻居的  start 。这样，邻居  PE 的  start 会在下一次  process 调
用时被使用。这正确模拟了硬件的一个时钟周期延迟。所以没问题。

这个方法精确地复制了硬件一个时钟上升沿的行为。

把左边 PE 刚刚锁存好的滤波器 复制到当前  PE 的输入端。
硬件中就是直接连线： filter_in[r][c] = filter_out[r][c-1] 。
注意这里用了  .copy()，避免 Python 对象引用导致的意外共享。

启动信号对角线传播 ：start 由左上角开始，通过  out_start  向右、向下传递。
这种设计 不要求输入像素在对角线方向上传递 ，而是依靠：
1. 调度器在每个时钟周期更新  data_port  上的数据（即新的输入行）。
2. 对角线启动信号让不同  PE 在不同时钟周期 锁存当时总线上的数据。
这样一来：
第 0 列 PE 最早锁存数据（例如行  0 ）；第  1 列  PE 晚  1 拍锁存（行  1 ）；第  2 列再晚  1 拍锁
存（行 2 ）。
在垂直方向，同一列的  PE 由于不同行启动时刻不同，也会锁存到不同行的数据（第  0 行  PE
最早，第  2 行  PE 最晚），从而实现滤波窗口在垂直方向的滑动。
结论：整个  3×3 阵列完成的是一个  3×3 滤波器在  5 行输入上的滑动，最终生成  3 个输出像
素，这三个像素就是输出特征图中某一行的相邻  3 个像素，分别由  第  0 列、第  1 列、第  2 列 的
底部 PE 输出。
所以：
❌ 只取中间列  →  丢失了左右两个输出像素，错误 。
✅ 必须将三列的底部  PE 输出都保留，拼接得到完整的三个输出像素。

滤波器行的乘加，然后垂直累加，所以底部 PE 的 result 已经是该列对应的最终输出像素的部分和（尚未

分别对应 3 个滑动窗口位置。那么 3x3 阵列中，同一列的 PE 在不同行使用不同滤波器行进行卷积，垂直
累加后，底部 PE 的 result 应该是该输出像素的三个部分和？实际上，在 2D 卷积中，每个输出像素需要
R*R次乘累加。 RS 将它分解为 R 个 1D 行卷积，每个 1D 行卷积产生一个部分和，这些部分和再累加得到最
终像素。因此，一个 PE 完成一个 1D 行卷积，产生 3 个输出像素的部分和（因为滑动窗产生 3 个值）。垂
直累加时，下部的 PE 要把上部传来的部分和与自己的部分和相加。在 pe_revised.v 中， PE 有 in_partial
和out_result ，都是 3 个值，垂直累加正是把三个部分和分别相加。因此，底部 PE 的 result 的三个值就
是最终输出行中三个像素的累加和（还需要加上其他通道的累加）。所以，一个 3x3 阵列输出 3 个像
素，正好对应底部 PE 的 result[0] 、 result[1] 、 result[2] 。但是这些 result 是来自底部每个 PE 的？不，底
部有三个 PE ，每个都有 3 个值的 result 。哪个代表最终的三个像素？应该是在同一列内，垂直累加是发
生在同一列的 PE 之间，不同列之间没有累加。因此，每一列独立产生三个输出像素？这会造成重复：
底部的第 0 列 PE 的 result[0], result[1], result[2] 是该列计算的三个像素；第 1 列 PE 也计算了三个像素；
第2列也是。那岂不是有 9 个像素？但这与 RS 的预期矛盾。我们需要仔细考虑广播数据 + 对角线启动的
简化方案是否真的等价于 RS 的逻辑 PE set 映射。
在标准RS 中，逻辑 PE set 的每一列处理不同的输出像素，每一行处理不同的滤波器行。列间不共享像素，
同一列内垂直累加产生一个输出像素。因此，每列底部只输出一个像素。但在我们的简化设计中，每个 PE
内部会滑动窗口产生 3 个输出，这暗示一个 PE 就同时计算了三个输出像素。为什么还要三列？其实这是因
为数据是广播的，所有 PE 看到相同的 5 个数据，但是滤波器由左侧传入，并且在启动信号的控制下，不同
列的PE在不同的时间锁存数据，导致它们实际上处理的是不同行的输入数据（因为数据端口在随时间变
化）。因此，一个 PE 处理的是某个输入行的 1D 卷积，产生 3 个部分和（对应三个输出像素），但这些部分
和还不是最终结果，因为还需要与使用其他滤波器行的 PE 结果累加（垂直累加）。垂直累加发生在同一列
的不同行 PE 之间。因此，最终底部 PE 的 result[0], [1], [2] 分别是用不同滤波器行处理同一输入行产生的部
分和累加？不对，部分和累加应该是为了合并不同滤波器行对同一输出像素的贡献。如果我们想得到输出
像素 O(x,y) = sum_{i,j} I(x +i,y+j) W(i,j)，将其拆分为对 i 的求和： O(x,y) = sum_ i (sum_ j
I(x +i,y +j)W(i,j))。对于固定的 i （滤波器行），内部是 1D 行卷积，产生一个中间部分和，这些部分和再对 i
求和得到最终 O 。因此，每个 PE 计算一个固定的 i （滤波器行），产生一个部分和向量（对应不同的 x 偏
移，即输出像素位置）。然后同一列不同行的 PE 分别对应不同的 i ，它们计算的部分和向量再相加，得到
最终输出像素向量。这样，一个 PE 的 result 的三个值应该是三个相邻输出像素的部分和（对应同一个滤波
器行i），而不是最终输出。垂直累加后，底部 PE 的 result 的三个值就是这三个输出像素的最终值（对本阵
列负责的部分）。因此，三列 PE 会分别处理不同的 x 偏移组吗？不，在 RS 的标准映射中，逻辑 PE set 的宽
度等于E（输出宽度），因此一个逻辑列对应一个输出像素。但是如果我们把滑动窗口放在 PE 内部，一个
PE就能计算多个输出像素（通过窗口滑动），那 PE set 的宽度就可以压缩。实际上 Eyeriss 的 PE 内部就是
进行1D卷积，产生多个部分和。论文中提到，每个 1D primitive 操作在一行滤波器权重和一行 ifmap 上，生
成一行部分和。这意味着一个 PE 产生一整行的部分和（ E 个值）。因此，一个逻辑列就足以生成一整行输
出（E个值）的部分和，不需要多个列。那么为什么还要多列呢？在论文的 Fig. 6 中，逻辑 PE set 的宽度是
E，但每个 PE 仍然负责一个输出像素，因为他们的 PE 内部可能没有滑动窗，或者滑动窗宽度为 1 。 Eyeriss
的具体PE 设计可能是一个 MAC 单元，每个周期计算一个乘法，需要多个周期滑动窗口。这和我们简化的
PE不同。我们简化的 PE 内部已经实现了完整滑动窗口，因此一个 PE 可以处理一个滤波器行对整行 ifmap 的
卷积，产生 E 个部分和。所以，在物理阵列中，我们只需要一列 PE 就可以完成垂直累加（不同滤波器
行），因为每个 PE 输出 E 个部分和。为什么还要用 3x3 的 PE 阵列？因为我们需要同时处理多个滤波器行和
多个输出通道？实际上，在我们的架构中， PE 阵列用于处理单个输入通道的卷积，输出部分和。一个 3x3
阵列中，三行 PE 分别处理三个滤波器行（ R=3 ），它们通过垂直累加将部分和相加，得到最终该通道对三
个输出像素的贡献（因为 E=3 ）。所以，每一列的 PE 是处理同一个输出像素吗？不，如果 PE 内部已经输出
了3个部分和（对应三个输出像素），那么垂直累加是这三个部分和分别相加。因此，同一列的三行 PE 会
累加，生成最终的三个输出像素。那左右两列呢？它们也各自独立地生成三个输出像素。但数据是广播
的，滤波器也是由左侧传入，只是时间不同。由于启动信号对角线传播，不同列 PE 的工作时间错开，它们
会处理不同时刻的数据。但数据总线只提供一行 ifmap ，并且在整个处理过程中保持不变（对于给定的
skip_row 和 out_f=0 ，数据行只更新一次），那么所有 PE 无论何时锁存，锁存到的都是同一行数据（因为
数据总线不变）。这样的话，三列 PE 锁存的数据相同，计算出的结果也相同，那么输出就有冗余。除非数
据总线在每个周期都更换不同行的数据，才能让不同列的 PE 处理不同行。这正是调度器的作用：它按
count顺序依次将 5 行 ifmap 数据放到 data_port 上，并配合启动信号，使得不同列 PE 在不同时间看到不同
行，从而实现不同滤波器行处理不同输入行。具体来说，对于每个 skip_row ，循环 count 从 0 到 4 ，每个
count更新 data_port 为对应的输入行，同时给出启动信号，从而激活对应行和列的 PE 。这样，阵列的第一
行PE在count=0 时锁存 skip_row+0 行，第二行 PE 在 count=1 时锁存 skip_row+1 行，第三行在 count=2 时
锁存skip_row+2 行；同一行中不同列启动时间也不同，但因为 data_port 在变化，它们可能锁存到不同
行？这需要严格的时序配合。实际上，在 scheduler .py 中， data_port 在每个 count 更新，并且只在前 4 个
count执行 process_st ep 。此外， filter_port 在 count<3 时更新滤波器行。最终输出地址在 count 1- 3 时推
入队列。这复杂的控制正是为了实现 RS 的垂直滑动。但无论如何，阵列底部的三个 PE 如果都完成了工
作，它们的 result 应该相同吗？如果数据总线按时间变化，配合启动的对角线传播，可以使不同行不同列

关键点在于： 在  count = 0  之前，调度器会专门设置  new_in_data = 1 ，让所有  PE 准备好锁
存新数据。  然后启动脉冲沿对角线传播，每一列  PE 被激活的瞬间，都会锁存 当时数据总线上
的值。
对角线启动保证了不同行  PE 锁存到不同行的数据 （通过时间差和总线更新配合）。
列与列之间的启动时间差保证了滤波器水平传播到位 。
因此，左列、中列、右列在锁存完所有需要的行数据后，各自都会算出正确的  3 个输出像素。

左列（col 0 ）：对应输入行  [0:5]，输出像素  0,1,2
中列（col 1 ）：对应输入行  [1:6]，输出像素  1,2,3
右列（col 2 ）：对应输入行  [2:7]，输出像素  2,3,4
所以取任何一个完成的最底部  PE ，都能得到  3 个有效的输出像素。  取第一个（最左列）是正确
且高效的，因为左列最先完成。
