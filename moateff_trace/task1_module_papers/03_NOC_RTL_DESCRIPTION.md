# Network-on-Chip (NoC): Register-Transfer-Level Description

## 1. Architectural Overview

The Network-on-Chip (NoC) is the data delivery infrastructure of the Eyeriss accelerator. It moves ifmap pixels, filter weights, and partial sums between off-chip DRAM (or global buffers, GLB) and the 12x14 PE array. The NoC is organized as a two-level multicast distribution tree: the Global Input Network (GIN) distributes data from a single source to multiple PE destinations, while the Global Output Network (GON) collects data from multiple PE sources into a single output stream. Both GIN and GON are built from identical primitive components -- Multicast Controllers (MCCs) and Crossbar Buses (XBuses) -- differing only in data flow direction (fan-out vs. fan-in).

The NoC is controlled by a hierarchical controller stack consisting of a pass_controller (top-level FSM), a noc_controller (channels orchestrator), four per-channel controllers (ifmap, filter, ipsum, opsum), and their associated index generators, tag generators, and address mappers. The entire system operates in lockstep across the four data channels, synchronized by a common start signal and completing when the opsum channel finishes (since opsum is always the last to complete).

## 2. Pass Controller: Top-Level Sequencing FSM

### 2.1 Module Function

The pass_controller is a simple four-state FSM that controls the execution of one "pass" -- the unit of data movement that delivers one slice of the convolution workload to the PE array. Its sole function is to generate the `start_nocs` pulse that launches all four NoC channels simultaneously, then wait for all channels to complete (`nocs_done`).

### 2.2 State Machine

The FSM transitions on `negedge clk` with combinational next-state and output logic:

1. **IDLE**: The controller waits for the external `start` signal (from the Scheduler). On `start`, it transitions to START_NOCS. Outputs `start_nocs`, `busy`, `done` are all deasserted.

2. **START_NOCS**: A single-cycle pulse state. It asserts `start_nocs = 1'b1` and unconditionally transitions to PROCESSING. The `start_nocs` pulse fans out to all four per-channel controllers (ifmap, filter, ipsum, opsum), which each contain their own index generators and FSMs.

3. **PROCESSING**: The controller asserts `busy = 1'b1` and waits for `nocs_done`. The `nocs_done` signal is generated by the noc_controller as the logical AND of the `done` outputs from all four channels (but critically, only `opsum_done` gates the completion, as described below). When asserted, the FSM transitions to DONE.

4. **DONE**: A single-cycle terminal state. Asserts `done = 1'b1` and unconditionally returns to IDLE.

### 2.3 Signal Timing

- `start_nocs`: A single-cycle pulse in START_NOCS state, derived combinatorially.
- `busy`: Asserted for the entire duration of PROCESSING.
- `done`: A single-cycle pulse in DONE state, indicating pass completion.

## 3. NoC Controller: Four-Channel Orchestrator

### 3.1 The Critical `done = opsum_done` Assignment

The noc_controller instantiates four per-channel controllers (ifmap, filter, ipsum, opsum) and wires their individual `done` outputs. The critical top-level assignment is:

```
assign done = opsum_done;
```

Only the opsum channel's completion matters for signaling overall NoC completion. This is because the opsum channel is always the last to finish: it must read back partial sums from the PE array after all computation is complete. The ifmap and filter channels finish delivering input data earlier; the ipsum channel delivers initial partial sums (or biases) at the start. The opsum channel reads results at the end, and its completion guarantees all data movement for the pass is finished.

### 3.2 Channel Instantiation

The noc_controller instantiates four controllers:

- **ifmap_noc_controller**: Manages ifmap data flow from GLB to PE array. Produces `ifmap_done`, GLB read address, GLB read enable, GIN write enable, and ifmap tags.
- **filter_noc_controller**: Manages filter data flow from GLB to PE array. Produces `filter_done`, GLB read address, GLB read enable, GIN write enable, and filter tags.
- **ipsum_noc_controller**: Manages input partial sum (and bias) data flow from GLB to PE array via GIN. Produces `ipsum_done`, two GLB addresses (ipsum and bias), GLB read enable, GIN write enable, and ipsum tags.
- **opsum_noc_controller**: Manages output partial sum data flow from PE array (via GON) back to GLB. Produces `opsum_done`, GLB write address, GON read enable, GLB write enable, and opsum tags.

### 3.3 Common Architecture of Per-Channel Controllers

All four per-channel controllers share an identical architectural template:

1. **Index Generator**: Produces a 4D index tuple (idx4, idx3, idx2, idx1) by looping through the data dimension space.
2. **Mapper**: Converts the 4D index tuple into a 1D global buffer address using a row-major or column-major address formula.
3. **Tag Generator**: Produces (row_tag, col_tag) pairs that route data to the correct PE row and column in the GIN/GON.
4. **Collector FIFO**: A depth-16 synchronous FIFO that buffers data between the GLB read side and the GIN/GON write side, providing rate decoupling.
5. **Flow Control**: A `flopr` (single-bit register) delays the `re_from_glb` signal by one clock cycle (on inverted clock) to produce the FIFO write enable, aligning the GLB read latency with the data arrival at the FIFO.

The data flow through each controller is:
1. Index generator asserts `re_from_glb` (busy) when ready and not awaiting.
2. GLB returns data `din` one cycle later.
3. The delayed `re_from_glb` (via flopr on `~clk`) becomes `we_to_collector`, writing the data into the collector FIFO.
4. Data is read from the collector FIFO when: `(~collector_empty) & (~gin_fifo_full) & (~tags_fifo_full)` for GIN-bound channels, or `(~gon_fifo_empty) & (~decollector_full)` for the GON-bound (opsum) channel.
5. Tag FIFO write enable is gated identically to data write enable, ensuring tags and data stay synchronized.

### 3.4 The Derived Parameter D

In the noc_controller, a critical combinational wire is computed:

```
assign D = (e << (U >> 1)) + R - U;
```

D represents the number of ifmap rows needed for the current convolution tile, accounting for the convolution stride U and filter height R. The expression `e << (U >> 1)` effectively multiplies e by an amount that depends on stride. This D value is passed to the ifmap_noc_controller as its row dimension parameter.

## 4. Ifmap Index Generator: Five-Level Nested Loop

### 4.1 Loop Structure

The ifmap_index_generator produces 4D indices through a deeply nested loop structure with five loop levels (counting from outermost to innermost):

1. **n (ifmap index)**: n_WIDTH bits -- outermost loop, iterates from 0 to n-1. This selects which ifmap group (channel group) to fetch.
2. **W (column index)**: W_WIDTH bits -- iterates from 0 to W-1. This selects the column within an ifmap row.
3. **q (channel sub-index)**: q_WIDTH bits -- iterates from 0 to q-1. This selects which filter-row group of channels.
4. **D (row index)**: D_WIDTH bits -- iterates from 0 to D-1. This selects the row within the ifmap.
5. **r (channel fine index)**: r_WIDTH bits -- innermost loop, iterates from 0 to r-1. This selects the fine-grained channel index within the q group.

### 4.2 State Machine and Counter Advancement

The index generator uses a five-state FSM (IDLE, LOOPING, OUTER_LOOP, INNER_LOOP, DONE) on `negedge clk`. Counter advancement follows a counter-overflow cascade:

Starting from the innermost loop (r), each counter increments until it reaches its bound minus one:
- r_crnt increments from 0 to r-1. On overflow, r resets to 0 and D increments.
- D_crnt increments from 0 to D-1. On overflow, D resets to 0 and q increments.
- q_crnt increments from 0 to q-1. On overflow, q resets to 0 and W increments.
- W_crnt increments from 0 to W-1. On overflow, W resets to 0 and n increments.
- n_crnt increments from 0 to n-1. On overflow, the FSM transitions to DONE.

### 4.3 The `await` Backpressure Signal

The `await` input (connected to `collector_full`) pauses the index generator when the collector FIFO is full. Within the LOOPING state, all advancement logic is gated by `if (!await)`. When `await` is asserted, the index generator holds its current state and deasserts `busy` (which gates `re_from_glb`), stalling the GLB read side until the GIN side drains the collector FIFO.

### 4.4 Output Index Computation

The four output indices are computed combinatorially from the current counters:
- `ifmap_index = n_crnt`: The ifmap group index.
- `channel_index = q_crnt + r_crnt * q`: The flat channel index combining q and r dimensions.
- `row_index = D_crnt`: The row within the ifmap.
- `col_index = W_crnt`: The column within the ifmap row.

The `channel_index` formula `q_crnt + r_crnt * q` interleaves channels: r varies fastest (inner), multiplied by q (the stride in the channel dimension), and added to q_crnt.

## 5. Filter and Psum Index Generators: Lock-Step Counter Mechanism

### 5.1 Filter Index Generator

The filter_index_generator employs a more complex 3-state FSM (IDLE, INNER_LOOP, OUTER_LOOP, DONE) with a distinctive lock-step mechanism. The loop structure is:

**INNER_LOOP** (innermost four levels, with `lock` protection):
- **i**: A fixed localparam `i = 4`, counting 4 iterations per inner loop cycle. Each iteration produces one index tuple, and the inner loop runs i times before yielding to OUTER_LOOP.
- **p (accumulator index)**: Iterates from 0 to p-1. On overflow, p resets and q advances.
- **q (filter row index)**: Iterates from 0 to q-1. On overflow, q resets and S advances.
- **S (filter column index)**: Iterates from 0 to S-1. On overflow, the `lock` flag is cleared (`lock_nxt = 0`), S resets.

**OUTER_LOOP** (outermost three levels):
- **t (filter slice index)**: Iterates from 0 to t-1. On overflow, r advances.
- **r (channel group index)**: Iterates from 0 to r-1. On overflow, R advances.
- **R (filter row dimension)**: Iterates from 0 to R-1. On overflow, if lock was already cleared, the state transitions to DONE. If lock was still asserted, the state returns to INNER_LOOP with `lock` re-asserted.

### 5.2 The Lock Mechanism

The `lock` flag is the key innovation in the filter_index_generator. It controls whether the INNER_LOOP's inner counters (p, q, S) advance or are held constant. The behavior is:

1. **lock = 1 on reset and at each OUTER_LOOP entry**: The INNER_LOOP advances through all p, q, S values, producing the full inner dimension sweep.
2. **When S overflows**: `lock` is cleared to 0. This allows the OUTER_LOOP to advance outer dimensions (t, r, R).
3. **On OUTER_LOOP re-entry**: `lock` is re-asserted to 1. However, the inner counters (p, q, S) are restored from their saved values (`p_reg_crnt`, `q_reg_crnt`, `S_reg_crnt`), not reset to zero. This implements "save and restore" semantics: the inner loop continues from where it left off rather than restarting from zero.

The save registers (`p_reg`, `q_reg`, `S_reg`) capture the current inner loop state each time the OUTER_LOOP completes a full cycle. When the OUTER_LOOP advances and re-enters INNER_LOOP, these saved values are loaded back into the active counters (`p_nxt = p_reg_crnt`, etc.), ensuring seamless continuation of the inner sweep.

This lock-step mechanism ensures that filter data is delivered in the correct order matching the PE's computation sequence, where weights are reused across multiple ifmap rows and channels.

### 5.3 Psum Index Generator

The psum_index_generator (shared between ipsum and opsum channels) uses the same lock-step architecture as the filter_index_generator, but with different dimension mappings and a crucial DONE-state update:

**Dimension mapping** (4D):
- idx4 = psum_index = n_crnt (ifmap group)
- idx3 = channel_index = m_crnt + p_crnt + (t_crnt * p) (output channel, combining m base + p accumulator + t slice)
- idx2 = row_index = e_crnt (ifmap row)
- idx1 = col_index = F_crnt (filter group)

**DONE state advancement**: Unlike the filter and ifmap index generators, the psum_index_generator updates the m_crnt counter in the DONE state:
```
if (m_crnt + (p * t) == m) begin
    m_nxt = 0;
end else begin
    m_nxt = m_crnt + (p * t);
end
```

This advancement of the output channel counter is performed once per complete psum index generation cycle, moving to the next output channel group. This mirrors the Scheduler's inner loop logic, keeping the psum addressing in sync with the overall computation order.

Note that the opsum_noc_controller runs the psum_index_generator on `posedge clk` (not `~clk`), with `await` connected to `decollector_empty` (wait for space in the output collector). The flow direction is reversed: data flows from GON to collector to GLB (write), rather than from GLB to collector to GIN (read).

## 6. The Mapper: 4D-to-1D Address Translation

### 6.1 Address Formula

The mapper converts a 4D index tuple (idx4, idx3, idx2, idx1) and 4D dimension tuple (dim4, dim3, dim2, dim1) into a flat linear address. The module is parameterized by `ROW_MAJOR` (0 or 1):

**Row-major** (ROW_MAJOR = 1):
```
addr = (idx4 * dim3 * dim2 * dim1) +
       (idx3 * dim2 * dim1) +
       (idx2 * dim1) +
        idx1;
```

**Column-major** (ROW_MAJOR = 0):
```
addr = (idx4 * dim3 * dim2 * dim1) +
       (idx3 * dim2 * dim1) +
       (idx1 * dim2) +
        idx2;
```

In both cases, index 4 is the outermost dimension (largest stride) and index 1 is the innermost (unit stride), but the ordering of dimension 1 and 2 is swapped between row-major and column-major. All channels in this design use `ROW_MAJOR = 1`.

### 6.2 Dimension Parameters by Data Type

Each data type has a different 4D dimension mapping:

| Data Type | dim4 (outer) | dim3 | dim2 | dim1 (inner) |
|-----------|-------------|------|------|-------------|
| Ifmap | n | q * r | D | W |
| Filter | p * t | q * r | R | S |
| Psum (ipsum/opsum/bias) | n | m | e | F |

For ifmap:
- dim4 = n (ifmap groups)
- dim3 = q * r (channels per pass)
- dim2 = D (rows = (e << (U>>1)) + R - U)
- dim1 = W (ifmap width)

For filter:
- dim4 = p * t (filter weights per pass)
- dim3 = q * r (channels per pass)  
- dim2 = R (filter height)
- dim1 = S (filter width)

For psum:
- dim4 = n (ifmap groups)
- dim3 = m (output channels)
- dim2 = e (ifmap rows per group)
- dim1 = F (filter groups)

The bias address in ipsum_noc_controller is a special case: `assign bias_addr = idx3` -- it uses only the output channel index (m dimension) as the address, since biases are a 1D vector indexed by output channel.

### 6.3 Mapper Instantiation Pattern

Each per-channel controller instantiates its own mapper with its specific dimension and index widths. The mapper is purely combinational -- the address is computed continuously from the current indices. The output address connects to the GLB interface port.

## 7. Tag Generators: PE Routing Information

Tags are the routing mechanism of the GIN/GON. Each data word traveling through the network carries a (row_tag, col_tag) pair that determines which PE row and column should receive (or send) the data.

### 7.1 Ifmap Tag Generator

The ifmap_tag_generator uses a 2-state FSM (IDLE, LOOPING) with three nested loops:

1. **r_crnt**: Innermost, 0 to r-1.
2. **U_crnt**: Middle, 0 to U-1.
3. **col_crnt**: Outermost, 0 to max_col_id, where `max_col_id = D >> (U >> 1)`.

The tag formulas are:
- **col_tag = col_crnt**: The column tag (identifies which PE column receives the data).
- **row_tag = U_crnt + (r_crnt * 4)**: The row tag combines U (stride offset) with r (channel group), multiplied by 4 (a fixed row stride in the PE array).

The total number of tag entries generated is `r * D`, matching the total number of ifmap pixels delivered. Tag generation is gated by the `enable` signal (connected to `rd_from_collector`), ensuring that tags are generated only when corresponding data is being sent to the GIN.

### 7.2 Filter Tag Generator

The filter_tag_generator is simpler, with a single 2-state FSM and three nested levels:
1. **t_crnt**: Innermost, 0 to t-1.
2. **r_crnt**: Middle, 0 to r-1.
3. **R_crnt**: Outermost, 0 to R-1.

Tag formulas:
- **col_tag = t_crnt + r_crnt * 2**: Column tag combining filter slice and channel group (each r group spans 2 columns).
- **row_tag = R_crnt**: Row tag is simply the filter row index.

### 7.3 Psum Tag Generator

The psum_tag_generator handles both the ipsum and opsum channels. It is the most complex tag generator, featuring two distinct operating modes depending on whether `e < 14`:

The generator walks through a 2D grid of (row, col) coordinates, driven by a `counter` that increments from 0 to `e*t - 1`. The grid dimensions are:
- `num_of_rows = (e * t + 13) >> 4` (ceiling division by 16, since 4 PEs share one row tag group)
- `num_of_cols = 14` (always 14 PE columns)

**When e < 14** (ifmap row groups fit within the PE array height):
The tag generator walks row-major through the (num_of_rows x num_of_cols) grid. Row increments first; when row reaches num_of_rows, column increments and row resets.

**When e >= 14** (ifmap rows span multiple PE array heights):
The tag generator walks column-major: column increments first; when column reaches num_of_cols, row increments and column resets.

This adaptive walk ensures that partial sums are routed to the correct PE positions regardless of whether the ifmap fits in a single vertical pass or requires multiple passes through the array.

The output tags are direct:
- **col_tag = col_crnt**
- **row_tag = row_crnt**

### 7.4 Opsum Tag Generator Special Behavior

In the opsum_noc_controller, the psum_tag_generator is instantiated with different connections than in the ipsum controller:
- `enable` is connected to `~tags_fifo_full` (not `rd_from_collector`), meaning tag generation continues as long as the tags FIFO has space.
- `busy` is connected to `we_to_tags_fifo`, providing a dedicated busy output for the tag write side.
- This asymmetry reflects the different flow direction: opsum tags are generated independently of data arrival from GON, while ipsum tags are generated in lockstep with data transmission to GIN.

## 8. GIN: Two-Level Multicast Distribution Network

### 8.1 Architecture

The Global Input Network (GIN) is a two-level multicast tree that distributes data from a single input port to multiple PEs in the 12x14 array. The architecture is:

**Level 1: Row Multicast (gin_mcc)**
For each of the 12 rows, a `gin_mcc` instance compares the incoming `row_tag` against its scan-chain-configured ID (`q_id`). When the tag matches and the output side is ready, the MCC forwards the data to the row's XBus. If the tag does not match, the MCC passes `ready_out` high (it is transparent to the flow control chain) but does not forward data.

**Level 2: Column Multicast (gin_xbus -> gin_mcc per column)**
For each row, a `gin_xbus` instance fans out the row data to all 14 columns. Within the XBus, each column has its own `gin_mcc` that compares the `col_tag` against its ID. Matching columns receive the data; non-matching columns are transparent to flow control.

### 8.2 GIN MCC (gin_mcc)

The gin_mcc is the fundamental routing cell. It has:
- A stored ID (`q_id`) loaded via scan chain at configuration time. Each MCC in the array (row MCCs and column MCCs) has a unique ID.
- A tag comparator: `equal_tag = (q_id == tag)`.
- Flow control: `ready_out = ready_in | (!equal_tag)`. If the tag does not match, the MCC reports ready regardless of downstream readiness -- it is bypassed. If the tag matches, it propagates the downstream ready signal.
- Data gating: `enable_mid = enable_in & ready_in & equal_tag`. Data is forwarded only when: (1) the input side has data (`enable_in`), (2) the output side is ready (`ready_in`), and (3) the tag matches. When enabled, `data_out = data_in`; otherwise, `data_out = 0`.

This design creates a distributed multicast: if multiple column MCCs have matching IDs (which never happens in this architecture since IDs are unique), all would receive the data simultaneously. In practice, each (row_tag, col_tag) pair targets exactly one PE location.

### 8.3 GIN XBus (gin_xbus)

The gin_xbus is a generate block that instantiates `NUM_OF_COLS` (14) gin_mcc instances in parallel, all receiving the same data and col_tag. Each MCC has a unique column ID loaded through a scan chain shift register. The XBus outputs are:
- `data_out[0:NUM_OF_COLS-1]`: Per-column data outputs.
- `enable_out[0:NUM_OF_COLS-1]`: Per-column write enables.
- `ready_out[i]`: The ready signal from each column MCC, ANDed to produce the XBus-level ready that feeds back to the row MCC.

### 8.4 GIN Tree Structure

The complete GIN tree in `gin.sv`:

```
data_in, row_tag, col_tag
    |
    +--[Row MCC 0]-->[XBus 0]--> col_mcc[0..13] --> data_out[0][0..13]
    +--[Row MCC 1]-->[XBus 1]--> col_mcc[0..13] --> data_out[1][0..13]
    ...
    +--[Row MCC 11]->[XBus 11]-> col_mcc[0..13] --> data_out[11][0..13]
```

The overall `ready_out` signal is the AND of all row MCC ready outputs: `assign ready_out = & mcc_ready;`. This means the GIN is ready to accept new data only when ALL rows are ready (or bypassed due to tag mismatch). Since only one row matches any given tag, only that row's downstream readiness matters; all other rows report ready unconditionally.

### 8.5 GIN Wrapper: FIFO Decoupling

The gin_wrapper surrounds the GIN with input FIFOs for data and tags:
- **Data FIFO**: Depth `GIN_DATA_FIFO_DEPTH` (16 for the PE array). Buffers data words before they enter the GIN tree.
- **Tags FIFO**: Depth `GIN_TAGS_FIFO_DEPTH` (16). Buffers (col_tag, row_tag) pairs. Notably, the FIFO stores tags in {col_tag, row_tag} order, but the GIN receives them unpacked: row_tag from the lower bits and col_tag from the upper bits.

The enable chain is: `enable_in = ready_out & ((~data_empty) & (~tags_empty))`. Data and tags are read from their FIFOs simultaneously only when the GIN is ready and both FIFOs have valid entries. This ensures tag-data synchronization.

### 8.6 Scan Chain Integration

Both row MCCs and column MCCs have their IDs loaded through a serial scan chain. The `gin.sv` module routes the scan path:
```
scan_in_id --> scan_w[0]
scan_w[0] --> Row MCC 0 scan_in
Row MCC 0 scan_out --> scan_w[1] --> XBus 0 scan_in
XBus 0 scan_out --> scan_w[2] --> Row MCC 1 scan_in
... 
XBus 11 scan_out --> scan_w[23] --> scan_out_id
```

Each MCC contains a `scan_ff_Nbit` register that captures its ID during scan configuration. The scan chain runs through all 12 rows * 2 (MCC + XBus per row) = 24 scan segments.

## 9. GON: Reverse Collection Network

### 9.1 Architectural Mirror

The Global Output Network (GON) is the reverse of the GIN. It collects data from the 12x14 PE array and aggregates it into a single output stream. The architecture mirrors the GIN:

**Level 1: Column Aggregation (gon_xbus -> gon_mcc per column)**
For each row, a `gon_xbus` aggregates data from all 14 columns. Each column's `gon_mcc` compares the `col_tag` against its ID. The matching column's data is selected and forwarded to the row MCC.

**Level 2: Row Aggregation (gon_mcc)**
For each row, a `gon_mcc` compares the `row_tag` against its row ID. The matching row's data is forwarded to the output.

### 9.2 GON MCC (gon_mcc)

The gon_mcc differs from the gin_mcc in two critical ways:

1. **Tristate output**: When the tag matches and the MCC is enabled, `data_out = data_in`. When not matching, `data_out = {DATA_WIDTH{1'bz}}` (high impedance). Multiple gon_mcc instances share the output bus, and the tag match mechanism ensures only one drives at a time. This is the fundamental difference between multicast (one-to-many) and aggregation (many-to-one).

2. **Ready logic**: `ready_out = ready_in | (!equal_tag)`. When the tag does not match, the MCC reports ready to its upstream (the PE or XBus) even if downstream is not ready, because it will not need to forward data. When the tag matches, it propagates downstream backpressure.

### 9.3 GON XBus (gon_xbus)

The gon_xbus mirrors the gin_xbus but operates in reverse: 14 gon_mcc instances share a common output bus (declared as `inout wire`). Each column's MCC receives data from its corresponding PE column. The tag match selects which column's data drives the shared output bus.

### 9.4 GON Wrapper: FIFO Decoupling

The gon_wrapper mirrors the gin_wrapper but with reversed flow:
- **Data flows**: PE array -> GON MCCs -> Data FIFO (write side) -> Output (read side).
- **Tags flow**: Tags arrive from the opsum tag generator into the Tags FIFO. Tags are read from the FIFO in sync with data collection: `enable_in = ready_out & ((~data_full) & (~tags_empty))`.
- **Output side**: Data is read from the output FIFO when the external controller asserts `data_rd_en` (connected to `opsum_re_from_gon_fifo`).

The `data_full` signal provides backpressure: when the output FIFO is full, the GON stops collecting data from PEs.

## 10. NoC Wrapper: Top-Level Integration

### 10.1 Hierarchy

The noc_wrapper sits between the Scheduler (control) and the PE array (data sink/source). It instantiates:
1. **pass_controller**: Receives `start` from the Scheduler, produces `start_nocs`.
2. **noc_controller**: Receives `start_nocs` from the pass_controller, manages all four channels.

### 10.2 Interface

The noc_wrapper exposes a comprehensive interface to the rest of the system:
- **Control**: `start`, `busy`, `done` handshake with the Scheduler.
- **Configuration**: All dimension parameters (H, W, R, S, E, F, U, m, n, e, p, q, r, t) passed through to noc_controller.
- **GLB Interface**: Read enables, write enables, and addresses for four channels (ifmap, filter, ipsum/bias, opsum).
- **GIN/GON Interface**: Write enables and data to/from the PE array's GIN/GON ports.
- **Tags**: Row and column tags for all four data types.
- **FIFO Status**: Full/empty flags from the PE array's GIN/GON FIFOs, used for flow control.

### 10.3 Data Width Transformations

The NoC performs key data width transformations:
- **Ifmap**: 16-bit GLB read -> 16-bit FIFO -> 16-bit GIN (no transformation).
- **Filter**: 16-bit GLB read -> 64-bit GIN output (4x packing in the collector FIFO).
- **Ipsum**: 16-bit GLB read -> 64-bit GIN output (4x packing).
- **Opsum**: 64-bit GON input -> 16-bit GLB write (4x unpacking).

The width conversion happens inside the `sync_fifo` instances, which are parameterized with different read and write data widths. This packing/unpacking amortizes the NoC overhead by transferring four 16-bit data words per network transaction on the 64-bit NoC buses.

## 11. Data Flow Timeline: One Complete Pass

The sequence of events for one pass is:

1. **Scheduler enters CHECK state** and waits for `start_pass`.
2. **Scheduler enters START_PASS**, asserts `start_noc`.
3. **pass_controller receives start**, enters START_NOCS, asserts `start_nocs`.
4. **All four index generators begin** looping through their dimension spaces:
   - Ifmap index generator produces (n, W, q, D, r) indices, mapper produces GLB address, tag generator produces (row_tag, col_tag).
   - Filter index generator produces (t, r, R, p, q, S) indices with lock-step.
   - Ipsum index generator produces (t, e, p, F, n) indices, plus bias address.
   - Opsum index generator produces (t, e, p, F, n) indices for output.
5. **GLB returns data** one cycle after each read request.
6. **Data flows through collector FIFOs** into GIN (ifmap, filter, ipsum) or waits in decollector (opsum).
7. **GIN distributes data** to PE array by matching row_tag and col_tag against MCC IDs.
8. **PE array computes** (the PROCESS state of each PE).
9. **GON collects results** from PE array using opsum tags.
10. **Opsum data flows** from GON -> decollector FIFO -> GLB write interface.
11. **When all opsum data is drained**, `opsum_done` asserts.
12. **noc_controller asserts `nocs_done`** (= opsum_done).
13. **pass_controller enters DONE**, asserts `done`.
14. **Scheduler receives noc_done**, enters PASS_DONE, asserts pass_done.
15. **Scheduler advances counters** in INNER_LOOP, returns to CHECK.

The critical insight is that the entire NoC operation is paced by the opsum channel. Ifmap, filter, and ipsum data delivery all complete before opsum data collection finishes, because the PEs must compute before results are available. The `done = opsum_done` assignment enforces this ordering at the hardware level.



























**片上网络（NoC）：寄存器传输级描述**

**1. 架构概述**

片上网络（NoC）是 Eyeriss 加速器的数据交付基础设施。它在片外 DRAM（或全局缓冲区 GLB）与 12x14 PE 阵列之间移动 ifmap 像素、滤波器权重和部分和。NoC 被组织为一个两级多播分发树：全局输入网络（GIN）将数据从单个源分发到多个 PE 目的地，而全局输出网络（GON）将数据从多个 PE 源收集到单个输出流中。GIN 和 GON 均由相同的基本组件构建——多播控制器（MCC）和交叉开关总线（XBus）——仅在数据流方向上不同（扇出与扇入）。

NoC 由一个分层控制器栈控制，包括一个 pass_controller（顶层 FSM）、一个 noc_controller（通道编排器）、四个每通道控制器（ifmap、filter、ipsum、opsum），以及它们关联的索引生成器、标签生成器和地址映射器。整个系统跨四个数据通道以锁步方式运行，由一个公共的 start 信号同步，并在 opsum 通道完成时完成（因为 opsum 总是最后完成的）。

**2. Pass 控制器：顶层定序 FSM**

**2.1 模块功能**

pass_controller 是一个简单的四状态 FSM，控制一个“处理趟”的执行——这是将卷积工作负载的一个切片传递到 PE 阵列的数据移动单元。它的唯一功能是生成 `start_nocs` 脉冲，同时启动所有四个 NoC 通道，然后等待所有通道完成（`nocs_done`）。

**2.2 状态机**

FSM 在 `negedge clk` 上以组合逻辑产生下一个状态和输出进行转换：

1.  **IDLE**：控制器等待来自外部的 `start` 信号（来自调度器）。在 `start` 时，它转换到 START_NOCS。输出 `start_nocs`、`busy`、`done` 均被取消断言。

2.  **START_NOCS**：一个单周期脉冲状态。它断言 `start_nocs = 1'b1` 并无条件转换到 PROCESSING。`start_nocs` 脉冲扇出到所有四个每通道控制器（ifmap、filter、ipsum、opsum），每个控制器都包含自己的索引生成器和 FSM。

3.  **PROCESSING**：控制器断言 `busy = 1'b1` 并等待 `nocs_done`。`nocs_done` 信号由 noc_controller 作为来自所有四个通道的 `done` 输出的逻辑与生成（但关键的是，只有 `opsum_done` 门控完成，如下所述）。当被断言时，FSM 转换到 DONE。

4.  **DONE**：一个单周期终止状态。断言 `done = 1'b1` 并无条件返回 IDLE。

**2.3 信号时序**

-   `start_nocs`：START_NOCS 状态中的一个单周期脉冲，以组合方式产生。
-   `busy`：在 PROCESSING 的整个持续时间内被断言。
-   `done`：DONE 状态中的一个单周期脉冲，指示处理趟完成。

**3. NoC 控制器：四通道编排器**

**3.1 关键的 `done = opsum_done` 赋值**

noc_controller 例化了四个每通道控制器（ifmap、filter、ipsum、opsum），并连线它们的各个 `done` 输出。关键的顶层赋值是：

```
assign done = opsum_done;
```

只有 opsum 通道的完成对于发信号表示整体 NoC 完成是重要的。这是因为 opsum 通道总是最后完成的：它必须在所有计算完成后从 PE 阵列读回部分和。ifmap 和 filter 通道更早完成输入数据的交付；ipsum 通道在开始时交付初始部分和（或偏置）。opsum 通道在最后读取结果，它的完成保证该处理趟的所有数据移动都已完成。

**3.2 通道例化**

noc_controller 例化了四个控制器：

-   **ifmap_noc_controller**：管理从 GLB 到 PE 阵列的 ifmap 数据流。产生 `ifmap_done`、GLB 读地址、GLB 读使能、GIN 写使能和 ifmap 标签。
-   **filter_noc_controller**：管理从 GLB 到 PE 阵列的滤波器数据流。产生 `filter_done`、GLB 读地址、GLB 读使能、GIN 写使能和滤波器标签。
-   **ipsum_noc_controller**：管理从 GLB 通过 GIN 到 PE 阵列的输入部分和（和偏置）数据流。产生 `ipsum_done`、两个 GLB 地址（ipsum 和 bias）、GLB 读使能、GIN 写使能和 ipsum 标签。
-   **opsum_noc_controller**：管理从 PE 阵列（通过 GON）回到 GLB 的输出部分和数据流。产生 `opsum_done`、GLB 写地址、GON 读使能、GLB 写使能和 opsum 标签。

**3.3 每通道控制器的通用架构**

所有四个每通道控制器共享一个相同的架构模板：

1.  **索引生成器**：通过循环遍历数据维度空间，产生一个 4D 索引元组（idx4, idx3, idx2, idx1）。
2.  **映射器**：使用行优先或列优先地址公式，将 4D 索引元组转换为 1D 全局缓冲区地址。
3.  **标签生成器**：产生（row_tag, col_tag）对，将数据路由到 GIN/GON 中正确的 PE 行和列。
4.  **收集器 FIFO**：一个深度为 16 的同步 FIFO，在 GLB 读侧和 GIN/GON 写侧之间缓冲数据，提供速率解耦。
5.  **流控制**：一个 `flopr`（单位寄存器）将 `re_from_glb` 信号延迟一个时钟周期（在反相时钟上），以产生 FIFO 写使能，将 GLB 读延迟与数据到达 FIFO 对齐。

数据流经每个控制器：
1.  索引生成器在就绪且未等待时断言 `re_from_glb`（busy）。
2.  GLB 在一个周期后返回数据 `din`。
3.  延迟的 `re_from_glb`（通过 `~clk` 上的 flopr）变为 `we_to_collector`，将数据写入收集器 FIFO。
4.  数据在以下条件下从收集器 FIFO 读出：对于 GIN 绑定通道，`(~collector_empty) & (~gin_fifo_full) & (~tags_fifo_full)`；对于 GON 绑定（opsum）通道，`(~gon_fifo_empty) & (~decollector_full)`。
5.  标签 FIFO 写使能与数据写使能相同地被门控，确保标签和数据保持同步。

**3.4 导出参数 D**

在 noc_controller 中，计算了一个关键的组合连线：

```
assign D = (e << (U >> 1)) + R - U;
```

D 表示当前卷积分块所需的 ifmap 行数，考虑了卷积步长 U 和滤波器高度 R。表达式 `e << (U >> 1)` 有效地将 e 乘以一个依赖于步长的量。此 D 值被传递给 ifmap_noc_controller 作为其行维度参数。

**4. Ifmap 索引生成器：五级嵌套循环**

**4.1 循环结构**

ifmap_index_generator 通过一个深度嵌套的循环结构产生 4D 索引，该结构具有五个循环层级（从最外层向最内层计数）：

1.  **n（ifmap 索引）**：n_WIDTH 位——最外层循环，从 0 迭代到 n-1。这选择取哪个 ifmap 组（通道组）。
2.  **W（列索引）**：W_WIDTH 位——从 0 迭代到 W-1。这选择 ifmap 行内的列。
3.  **q（通道子索引）**：q_WIDTH 位——从 0 迭代到 q-1。这选择哪个滤波器行组的通道。
4.  **D（行索引）**：D_WIDTH 位——从 0 迭代到 D-1。这选择 ifmap 内的行。
5.  **r（通道精细索引）**：r_WIDTH 位——最内层循环，从 0 迭代到 r-1。这选择 q 组内的细粒度通道索引。

**4.2 状态机和计数器推进**

索引生成器在 `negedge clk` 上使用一个五状态 FSM（IDLE、LOOPING、OUTER_LOOP、INNER_LOOP、DONE）。计数器推进遵循一个计数器溢出级联：

从最内层循环（r）开始，每个计数器递增直到到达其绑定减一：
-   r_crnt 从 0 递增到 r-1。溢出时，r 复位到 0，D 递增。
-   D_crnt 从 0 递增到 D-1。溢出时，D 复位到 0，q 递增。
-   q_crnt 从 0 递增到 q-1。溢出时，q 复位到 0，W 递增。
-   W_crnt 从 0 递增到 W-1。溢出时，W 复位到 0，n 递增。
-   n_crnt 从 0 递增到 n-1。溢出时，FSM 转换到 DONE。

**4.3 `await` 反压信号**

`await` 输入（连接到 `collector_full`）在收集器 FIFO 满时暂停索引生成器。在 LOOPING 状态内，所有推进逻辑由 `if (!await)` 门控。当 `await` 被断言时，索引生成器保持其当前状态并取消断言 `busy`（这门控 `re_from_glb`），暂停 GLB 读侧，直到 GIN 侧排空收集器 FIFO。

**4.4 输出索引计算**

四个输出索引是从当前计数器以组合方式计算的：
-   `ifmap_index = n_crnt`：ifmap 组索引。
-   `channel_index = q_crnt + r_crnt * q`：合并 q 和 r 维度的扁平通道索引。
-   `row_index = D_crnt`：ifmap 内的行。
-   `col_index = W_crnt`：ifmap 行内的列。

`channel_index` 公式 `q_crnt + r_crnt * q` 交错通道：r 变化最快（内侧），乘以 q（通道维度中的步长），并加到 q_crnt 上。

**5. 滤波器和 Psum 索引生成器：锁步计数器机制**

**5.1 滤波器索引生成器**

filter_index_generator 使用一个更复杂的三状态 FSM（IDLE、INNER_LOOP、OUTER_LOOP、DONE），具有独特的锁步机制。循环结构如下：

**INNER_LOOP**（最内层四个层级，具有 `lock` 保护）：
-   **i**：一个固定的 localparam `i = 4`，每个内层循环周期计数 4 次迭代。每次迭代产生一个索引元组，内层循环在让给 OUTER_LOOP 之前运行 i 次。
-   **p（累加器索引）**：从 0 迭代到 p-1。溢出时，p 复位，q 推进。
-   **q（滤波器行索引）**：从 0 迭代到 q-1。溢出时，q 复位，S 推进。
-   **S（滤波器列索引）**：从 0 迭代到 S-1。溢出时，`lock` 标志被清除（`lock_nxt = 0`），S 复位。

**OUTER_LOOP**（最外层三个层级）：
-   **t（滤波器切片索引）**：从 0 迭代到 t-1。溢出时，r 推进。
-   **r（通道组索引）**：从 0 迭代到 r-1。溢出时，R 推进。
-   **R（滤波器行维度）**：从 0 迭代到 R-1。溢出时，如果 lock 已经被清除，状态转换到 DONE。如果 lock 仍被断言，状态返回 INNER_LOOP，`lock` 重新被断言。

**5.2 锁机制**

`lock` 标志是 filter_index_generator 中的关键创新。它控制 INNER_LOOP 的内部计数器（p、q、S）是推进还是保持不变。行为如下：

1.  **lock = 1，在复位时和每次 OUTER_LOOP 入口处**：INNER_LOOP 推进所有 p、q、S 值，产生完整的内维度扫描。
2.  **当 S 溢出时**：`lock` 被清除为 0。这允许 OUTER_LOOP 推进外部维度（t、r、R）。
3.  **在 OUTER_LOOP 重新进入时**：`lock` 被重新断言为 1。然而，内部计数器（p、q、S）从其保存的值（`p_reg_crnt`、`q_reg_crnt`、`S_reg_crnt`）恢复，而不是复位到零。这实现了“保存和恢复”语义：内层循环从其离开的地方继续，而不是从零重新开始。

保存寄存器（`p_reg`、`q_reg`、`S_reg`）在 OUTER_LOOP 每次完成一个完整周期时捕获当前的内层循环状态。当 OUTER_LOOP 推进并重新进入 INNER_LOOP 时，这些保存的值被加载回活跃计数器（`p_nxt = p_reg_crnt` 等），确保内层扫描的无缝继续。

此锁步机制确保滤波器数据按照与 PE 计算序列匹配的正确顺序交付，其中权重跨多个 ifmap 行和通道被重用。

**5.3 Psum 索引生成器**

psum_index_generator（在 ipsum 和 opsum 通道之间共享）使用与 filter_index_generator 相同的锁步架构，但具有不同的维度映射和一个关键的 DONE 状态更新：

**维度映射**（4D）：
-   idx4 = psum_index = n_crnt（ifmap 组）
-   idx3 = channel_index = m_crnt + p_crnt + (t_crnt * p)（输出通道，结合 m 基址 + p 累加器 + t 切片）
-   idx2 = row_index = e_crnt（ifmap 行）
-   idx1 = col_index = F_crnt（滤波器组）

**DONE 状态推进**：与滤波器和 ifmap 索引生成器不同，psum_index_generator 在 DONE 状态中更新 m_crnt 计数器：
```
if (m_crnt + (p * t) == m) begin
    m_nxt = 0;
end else begin
    m_nxt = m_crnt + (p * t);
end
```

输出通道计数器的这种推进在每个完整的 psum 索引生成周期执行一次，移动到下一个输出通道组。这镜像了调度器的内层循环逻辑，使 psum 寻址与整体计算顺序保持同步。

注意，opsum_noc_controller 在 `posedge clk` 上运行 psum_index_generator（不是 `~clk`），`await` 连接到 `decollector_empty`（等待输出收集器中的空间）。流方向是反向的：数据从 GON 流向收集器再流向 GLB（写），而不是从 GLB 流向收集器再流向 GIN（读）。

**6. 映射器：4D 到 1D 地址转换**

**6.1 地址公式**

映射器将一个 4D 索引元组（idx4、idx3、idx2、idx1）和一个 4D 维度元组（dim4、dim3、dim2、dim1）转换为一个扁平的线性地址。该模块由 `ROW_MAJOR`（0 或 1）参数化：

**行优先**（ROW_MAJOR = 1）：
```
addr = (idx4 * dim3 * dim2 * dim1) +
       (idx3 * dim2 * dim1) +
       (idx2 * dim1) +
        idx1;
```

**列优先**（ROW_MAJOR = 0）：
```
addr = (idx4 * dim3 * dim2 * dim1) +
       (idx3 * dim2 * dim1) +
       (idx1 * dim2) +
        idx2;
```

在这两种情况下，索引 4 是最外层维度（最大步长），索引 1 是最内层（单位步长），但维度 1 和 2 的顺序在行优先和列优先之间互换。此设计中的所有通道都使用 `ROW_MAJOR = 1`。

**6.2 各数据类型的维度参数**

每种数据类型都有不同的 4D 维度映射：

| 数据类型 | dim4（外层） | dim3 | dim2 | dim1（内层） |
|---|---|---|---|---|
| Ifmap | n | q * r | D | W |
| Filter | p * t | q * r | R | S |
| Psum（ipsum/opsum/bias） | n | m | e | F |

对于 ifmap：
-   dim4 = n（ifmap 组）
-   dim3 = q * r（每趟通道数）
-   dim2 = D（行数 = (e << (U>>1)) + R - U）
-   dim1 = W（ifmap 宽度）

对于滤波器：
-   dim4 = p * t（每趟滤波器权重数）
-   dim3 = q * r（每趟通道数）
-   dim2 = R（滤波器高度）
-   dim1 = S（滤波器宽度）

对于 psum：
-   dim4 = n（ifmap 组）
-   dim3 = m（输出通道数）
-   dim2 = e（每组 ifmap 行数）
-   dim1 = F（滤波器组数）

ipsum_noc_controller 中的偏置地址是一个特例：`assign bias_addr = idx3`——它仅使用输出通道索引（m 维度）作为地址，因为偏置是一个按输出通道索引的 1D 向量。

**6.3 映射器例化模式**

每个每通道控制器用其特定的维度和索引宽度例化自己的映射器。映射器是纯组合逻辑的——地址从当前索引连续计算。输出地址连接到 GLB 接口端口。

**7. 标签生成器：PE 路由信息**

标签是 GIN/GON 的路由机制。通过网络传输的每个数据字携带一个（row_tag, col_tag）对，它决定哪个 PE 行和列应该接收（或发送）该数据。

**7.1 Ifmap 标签生成器**

ifmap_tag_generator 使用一个具有三个嵌套循环的 2 状态 FSM（IDLE、LOOPING）：

1.  **r_crnt**：最内层，0 到 r-1。
2.  **U_crnt**：中间，0 到 U-1。
3.  **col_crnt**：最外层，0 到 max_col_id，其中 `max_col_id = D >> (U >> 1)`。

标签公式为：
-   **col_tag = col_crnt**：列标签（标识哪个 PE 列接收数据）。
-   **row_tag = U_crnt + (r_crnt * 4)**：行标签将 U（步长偏移）与 r（通道组）结合，乘以 4（PE 阵列中的固定行步长）。

生成的标签条目总数是 `r * D`，与交付的 ifmap 像素总数匹配。标签生成由 `enable` 信号（连接到 `rd_from_collector`）门控，确保只有当相应数据被发送到 GIN 时才生成标签。

**7.2 滤波器标签生成器**

filter_tag_generator 更简单，具有一个单 2 状态 FSM 和三个嵌套层级：
1.  **t_crnt**：最内层，0 到 t-1。
2.  **r_crnt**：中间，0 到 r-1。
3.  **R_crnt**：最外层，0 到 R-1。

标签公式：
-   **col_tag = t_crnt + r_crnt * 2**：列标签结合滤波器切片和通道组（每个 r 组跨越 2 列）。
-   **row_tag = R_crnt**：行标签就是滤波器行索引。

**7.3 Psum 标签生成器**

psum_tag_generator 处理 ipsum 和 opsum 两个通道。它是最复杂的标签生成器，具有两种不同的操作模式，取决于 `e < 14` 是否成立：

生成器遍历一个由（row, col）坐标组成的 2D 网格，由一个 `counter` 驱动，该计数器从 0 递增到 `e*t - 1`。网格维度为：
-   `num_of_rows = (e * t + 13) >> 4`（除以 16 的向上取整，因为 4 个 PE 共享一个行标签组）
-   `num_of_cols = 14`（总是 14 个 PE 列）

**当 e < 14 时**（ifmap 行组适配在 PE 阵列高度内）：
标签生成器行优先地遍历（num_of_rows x num_of_cols）网格。行先递增；当行到达 num_of_rows 时，列递增，行复位。

**当 e >= 14 时**（ifmap 行跨越多个 PE 阵列高度）：
标签生成器列优先地遍历：列先递增；当列到达 num_of_cols 时，行递增，列复位。

这种自适应遍历确保部分和被路由到正确的 PE 位置，无论 ifmap 是否适配在单个垂直趟中，还是需要多趟通过阵列。

输出标签是直接的：
-   **col_tag = col_crnt**
-   **row_tag = row_crnt**

**7.4 Opsum 标签生成器的特殊行为**

在 opsum_noc_controller 中，psum_tag_generator 被例化为与 ipsum 控制器中不同的连接：
-   `enable` 连接到 `~tags_fifo_full`（不是 `rd_from_collector`），意味着只要标签 FIFO 有空间，标签生成就会继续。
-   `busy` 连接到 `we_to_tags_fifo`，为标签写侧提供一个专用的 busy 输出。
-   这种不对称反映了不同的流方向：opsum 标签独立于来自 GON 的数据到达而生成，而 ipsum 标签则与数据传输到 GIN 锁步生成。

**8. GIN：两级多播分发网络**

**8.1 架构**

全局输入网络（GIN）是一个两级多播树，将数据从单个输入端口分发到 12x14 阵列中的多个 PE。架构如下：

**第一级：行多播（gin_mcc）**
对于 12 行中的每一行，一个 `gin_mcc` 实例将传入的 `row_tag` 与其通过扫描链配置的 ID（`q_id`）进行比较。当标签匹配且输出侧就绪时，MCC 将数据转发到该行的 XBus。如果标签不匹配，MCC 将 `ready_out` 传递为高（它对流控制链是透明的），但不转发数据。

**第二级：列多播（gin_xbus -> 每列的 gin_mcc）**
对于每一行，一个 `gin_xbus` 实例将行数据扇出到所有 14 列。在 XBus 内，每列都有自己的 `gin_mcc`，将 `col_tag` 与其 ID 进行比较。匹配的列接收数据；不匹配的列对流控制是透明的。

**8.2 GIN MCC（gin_mcc）**

gin_mcc 是基本的路由单元。它具有：
-   一个存储的 ID（`q_id`），在配置时通过扫描链加载。阵列中的每个 MCC（行 MCC 和列 MCC）都有一个唯一的 ID。
-   一个标签比较器：`equal_tag = (q_id == tag)`。
-   流控制：`ready_out = ready_in | (!equal_tag)`。如果标签不匹配，MCC 不论下游就绪与否都报告就绪——它被旁路。如果标签匹配，它传播下游的 ready 信号。
-   数据门控：`enable_mid = enable_in & ready_in & equal_tag`。数据仅在以下情况下被转发：(1) 输入侧有数据（`enable_in`），(2) 输出侧就绪（`ready_in`），以及 (3) 标签匹配。当启用时，`data_out = data_in`；否则，`data_out = 0`。

此设计创建了一个分布式多播：如果多个列 MCC 具有匹配的 ID（在此架构中从未发生，因为 ID 是唯一的），所有列将同时接收数据。在实践中，每个（row_tag, col_tag）对恰好以一个 PE 位置为目标。

**8.3 GIN XBus（gin_xbus）**

gin_xbus 是一个 generate 块，并行例化 `NUM_OF_COLS`（14）个 gin_mcc 实例，所有实例接收相同的数据和 col_tag。每个 MCC 都有一个通过扫描链移位寄存器加载的唯一列 ID。XBus 输出为：
-   `data_out[0:NUM_OF_COLS-1]`：每列数据输出。
-   `enable_out[0:NUM_OF_COLS-1]`：每列写使能。
-   `ready_out[i]`：来自每个列 MCC 的 ready 信号，经过“与”操作产生反馈给行 MCC 的 XBus 级 ready。

**8.4 GIN 树结构**

`gin.sv` 中的完整 GIN 树：

```
data_in, row_tag, col_tag
    |
    +--[Row MCC 0]-->[XBus 0]--> col_mcc[0..13] --> data_out[0][0..13]
    +--[Row MCC 1]-->[XBus 1]--> col_mcc[0..13] --> data_out[1][0..13]
    ...
    +--[Row MCC 11]->[XBus 11]-> col_mcc[0..13] --> data_out[11][0..13]
```

整体 `ready_out` 信号是所有行 MCC ready 输出的逻辑与：`assign ready_out = & mcc_ready;`。这意味着 GIN 仅在所有行都就绪（或因标签不匹配而被旁路）时才准备接受新数据。由于对于任何给定标签只有一行匹配，只有该行的下游就绪状态是重要的；所有其他行无条件报告就绪。

**8.5 GIN 封装器：FIFO 解耦**

gin_wrapper 用用于数据和标签的输入 FIFO 包围 GIN：
-   **数据 FIFO**：深度 `GIN_DATA_FIFO_DEPTH`（对于 PE 阵列为 16）。在数据字进入 GIN 树之前对其进行缓冲。
-   **标签 FIFO**：深度 `GIN_TAGS_FIFO_DEPTH`（16）。缓冲（col_tag, row_tag）对。值得注意的是，FIFO 以 {col_tag, row_tag} 的顺序存储标签，但 GIN 以解包形式接收它们：row_tag 来自低位，col_tag 来自高位。

使能链为：`enable_in = ready_out & ((~data_empty) & (~tags_empty))`。只有当 GIN 就绪且两个 FIFO 都有有效条目时，数据和标签才同时从它们的 FIFO 中读出。这确保了标签与数据的同步。

**8.6 扫描链集成**

行 MCC 和列 MCC 都有通过串行扫描链加载的 ID。`gin.sv` 模块路由扫描路径：
```
scan_in_id --> scan_w[0]
scan_w[0] --> Row MCC 0 scan_in
Row MCC 0 scan_out --> scan_w[1] --> XBus 0 scan_in
XBus 0 scan_out --> scan_w[2] --> Row MCC 1 scan_in
... 
XBus 11 scan_out --> scan_w[23] --> scan_out_id
```

每个 MCC 包含一个 `scan_ff_Nbit` 寄存器，在扫描配置期间捕获其 ID。扫描链贯穿所有 12 行 * 2（每行 MCC + XBus）= 24 个扫描段。

**9. GON：反向收集网络**

**9.1 架构镜像**

全局输出网络（GON）是 GIN 的反向。它从 12x14 PE 阵列收集数据，并将其聚合到单一输出流中。架构镜像 GIN：

**第一级：列聚合（gon_xbus -> 每列的 gon_mcc）**
对于每一行，一个 `gon_xbus` 聚合来自所有 14 列的数据。每列的 `gon_mcc` 将 `col_tag` 与其 ID 进行比较。匹配列的数据被选择并转发到行 MCC。

**第二级：行聚合（gon_mcc）**
对于每一行，一个 `gon_mcc` 将 `row_tag` 与其行 ID 进行比较。匹配行的数据被转发到输出。

**9.2 GON MCC（gon_mcc）**

gon_mcc 在两个关键方面与 gin_mcc 不同：

1.  **三态输出**：当标签匹配且 MCC 被启用时，`data_out = data_in`。当不匹配时，`data_out = {DATA_WIDTH{1'bz}}`（高阻抗）。多个 gon_mcc 实例共享输出总线，标签匹配机制确保每次只有一个驱动。这是多播（一对多）和聚合（多对一）之间的根本区别。

2.  **就绪逻辑**：`ready_out = ready_in | (!equal_tag)`。当标签不匹配时，MCC 向其上游（PE 或 XBus）报告就绪，即使下游未就绪，因为它不需要转发数据。当标签匹配时，它传播下游反压。

**9.3 GON XBus（gon_xbus）**

gon_xbus 镜像 gin_xbus，但以反向操作：14 个 gon_mcc 实例共享一个公共输出总线（声明为 `inout wire`）。每列的 MCC 从对应的 PE 列接收数据。标签匹配选择哪一列的数据驱动共享输出总线。

**9.4 GON 封装器：FIFO 解耦**

gon_wrapper 镜像 gin_wrapper，但流方向相反：
-   **数据流**：PE 阵列 -> GON MCC -> 数据 FIFO（写侧）-> 输出（读侧）。
-   **标签流**：标签从 opsum 标签生成器到达标签 FIFO。标签与数据收集同步地从 FIFO 读出：`enable_in = ready_out & ((~data_full) & (~tags_empty))`。
-   **输出侧**：当外部控制器断言 `data_rd_en`（连接到 `opsum_re_from_gon_fifo`）时，数据从输出 FIFO 读出。

`data_full` 信号提供反压：当输出 FIFO 满时，GON 停止从 PE 收集数据。

**10. NoC 封装器：顶层集成**

**10.1 层次结构**

noc_wrapper 位于调度器（控制）和 PE 阵列（数据宿/源）之间。它例化：
1.  **pass_controller**：从调度器接收 `start`，产生 `start_nocs`。
2.  **noc_controller**：从 pass_controller 接收 `start_nocs`，管理所有四个通道。

**10.2 接口**

noc_wrapper 向系统的其余部分公开一个全面的接口：
-   **控制**：与调度器的 `start`、`busy`、`done` 握手。
-   **配置**：所有维度参数（H、W、R、S、E、F、U、m、n、e、p、q、r、t）传递给 noc_controller。
-   **GLB 接口**：四个通道（ifmap、filter、ipsum/bias、opsum）的读使能、写使能和地址。
-   **GIN/GON 接口**：来自/去往 PE 阵列的 GIN/GON 端口的写使能和数据。
-   **标签**：所有四种数据类型的行和列标签。
-   **FIFO 状态**：来自 PE 阵列的 GIN/GON FIFO 的满/空标志，用于流控制。

**10.3 数据宽度转换**

NoC 执行关键的数据宽度转换：
-   **Ifmap**：16 位 GLB 读 -> 16 位 FIFO -> 16 位 GIN（无转换）。
-   **滤波器**：16 位 GLB 读 -> 64 位 GIN 输出（在收集器 FIFO 中 4x 打包）。
-   **Ipsum**：16 位 GLB 读 -> 64 位 GIN 输出（4x 打包）。
-   **Opsum**：64 位 GON 输入 -> 16 位 GLB 写（4x 解包）。

宽度转换发生在 `sync_fifo` 实例内部，这些实例用不同的读写数据宽度参数化。这种打包/解包通过在 64 位 NoC 总线上每次网络事务传输四个 16 位数据字来平摊 NoC 开销。

**11. 数据流时间线：一个完整的处理趟**

一个处理趟的事件序列如下：

1.  **调度器进入 CHECK 状态**，等待 `start_pass`。
2.  **调度器进入 START_PASS**，断言 `start_noc`。
3.  **pass_controller 接收 start**，进入 START_NOCS，断言 `start_nocs`。
4.  **所有四个索引生成器开始**循环遍历其维度空间：
    -   Ifmap 索引生成器产生（n, W, q, D, r）索引，映射器产生 GLB 地址，标签生成器产生（row_tag, col_tag）。
    -   滤波器索引生成器以锁步方式产生（t, r, R, p, q, S）索引。
    -   Ipsum 索引生成器产生（t, e, p, F, n）索引，外加偏置地址。
    -   Opsum 索引生成器为输出产生（t, e, p, F, n）索引。
5.  **GLB 在每次读请求后一个周期返回数据**。
6.  **数据流经收集器 FIFO** 进入 GIN（ifmap、filter、ipsum），或在 decollector 中等待（opsum）。
7.  **GIN 将数据分发**到 PE 阵列，通过将 row_tag 和 col_tag 与 MCC ID 进行匹配。
8.  **PE 阵列计算**（每个 PE 的 PROCESS 状态）。
9.  **GON 使用 opsum 标签从 PE 阵列收集结果**。
10. **Opsum 数据流**从 GON -> decollector FIFO -> GLB 写接口。
11. **当所有 opsum 数据被排空时**，`opsum_done` 断言。
12. **noc_controller 断言 `nocs_done`**（= opsum_done）。
13. **pass_controller 进入 DONE**，断言 `done`。
14. **调度器接收 noc_done**，进入 PASS_DONE，断言 pass_done。
15. **调度器在 INNER_LOOP 中推进计数器**，返回 CHECK。

关键的洞察是，整个 NoC 操作由 opsum 通道调节节奏。Ifmap、filter 和 ipsum 的数据交付都在 opsum 数据收集完成之前完成，因为 PE 在结果可用之前必须先计算。`done = opsum_done` 赋值在硬件级别强制执行此排序。
